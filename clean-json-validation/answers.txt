CCAF Day 9-10 — Applied Answers

1. Caching

Reason:
The same large context is reused across many requests, so prompt caching
is the appropriate choice.

2. Batching

Reason:
The requests do not need immediate responses, so Batch API is appropriate.

3. Neither

Reason:
The workload does not have repeated context that would benefit from
caching, and the result is needed immediately, so batching is also not
appropriate.

4. Batching

Reason:
The requests can be processed asynchronously and do not require
immediate responses.

5. Neither

Reason:
There is no meaningful repeated context for caching and the response
needs to be available immediately.

6. Caching

Reason:
The same large prompt/context is repeatedly sent, so caching avoids
reprocessing the same input.

SELF-CHECK

1. What does a cache read cost relative to normal input?

Answer:
0.10x the normal input price.

2. What does a 5-minute cache write cost?

Answer:
1.25x the normal input price.

3. Which usage field proves a cache write happened?

Answer:
cache_creation_input_tokens

4. Which usage field proves a cache read happened?

Answer:
cache_read_input_tokens

5. What happens if the cached prefix is below the model's minimum
token floor?

Answer:
Caching does not engage.

6. How do you match a Batch API result to the original request?

Answer:
Use custom_id.

7. What is the main question when deciding between synchronous
processing and Batch API?

Answer:
"Is anyone waiting for this answer right now?"
